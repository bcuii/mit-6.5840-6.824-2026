## 〇、概览

GFS 跑在几千台廉价商用机器上，为**大文件、高吞吐、追加写**的批处理负载设计。

架构是**一个 master + 大量 chunkserver**。文件切成固定 **64MB 的 chunk**，默认 **3 副本**跨机架存放。最核心的一点是**控制流与数据流分离**：客户端只向 master 问"数据在哪台机器"，然后**直连 chunkserver 读写**，数据一个字节都不经过 master —— 这是单 master 不成为瓶颈的根本原因。

写入用**租约（lease）**：master 把某个 chunk 的租约授予一个副本作为 **primary**，由 primary 为并发变更**定序**，所有副本按同一顺序应用。master 连定序权也下放了。

最有特色的接口是 **atomic record append**：客户端只给数据、不指定 offset，由 GFS 决定位置并返回，保证**原子地至少写入一次**。几百个生产者可以无锁并发追加同一个文件。

代价是**一致性模型很弱**：并发写的区域 consistent 但 undefined，record append 还会留下 padding 和重复记录。GFS 把去重和校验推给应用层，换来系统本身的极度简洁。

一句话总结设计哲学：**先精确定义你的负载，然后为这个负载放弃所有你不需要的通用性。**

## 一、设计前提（Section 1–2.2）

GFS 所有"奇怪"的选择都能从这五条假设推出来。

| 假设 | 推出的设计 |
|---|---|
| **故障是常态** —— 上千台廉价机器随时挂 | 复制、监控、自动恢复是主干逻辑，不是补丁 |
| **文件极大** —— GB 级，几百万个 | 64MB 大 chunk；不为小文件优化 |
| **以追加为主，写完就只读** | 为顺序追加优化一切；随机覆盖写"支持但不保证高效" |
| **高吞吐 >> 低延迟** | 流水线推数据、批量刷日志，都是拿延迟换带宽 |
| **应用与文件系统协同设计** | 敢于放宽一致性、敢于加 `record append` 这种非标准接口 |

**接口不兼容 POSIX**，这是个被低估的决策 —— 不用接入内核 vnode 层，可以纯用户态库实现，接口语义完全自由，才有了 `snapshot` 和 `record append`。

## 二、架构与单 master（Section 2.3–2.5）

| 角色 | 职责 |
|---|---|
| **master**（单个） | 全部元数据、租约管理、垃圾回收、chunk 迁移与再复制。**不碰任何文件数据** |
| **chunkserver** | 把 chunk 当作**普通 Linux 文件**存在本地磁盘 |
| **client** | 以库形式链接进应用，**直连 chunkserver 传数据** |

**单 master 为什么不是瓶颈**：

1. **数据不走 master**。问一次位置，之后所有 I/O 直连 chunkserver。
2. **元数据全在内存**。每个 chunk **< 64 字节**，每个文件的命名空间数据也 **< 64 字节**（文件名**前缀压缩**）。实测集群 master 元数据只有几十 MB。
3. **客户端缓存 + 批量预取**。位置信息带超时地缓存；一次请求还会**顺带预取后续几个 chunk 的位置**。
4. **大 chunk 摊薄交互**。读一个大文件只需极少次元数据请求。

**为什么 chunk 是 64MB**：减少 client↔master 交互、可对同一 chunk 复用**持久 TCP 连接**、压缩 master 元数据体量。代价是小文件只占一两个 chunk，被大量客户端并发访问会形成**热点**（论文提到一个单 chunk 的可执行文件被几百台机器同时读取，压垮了 chunkserver；修法是提高该文件的复制因子 + 错开启动时间）。

> ⚠️ **常见误解**：小文件**不会**真的占满 64MB。chunk 就是个普通 Linux 文件，采用**惰性空间分配**按需扩展。论文明确用这一点回应"大 chunk 浪费空间"的质疑。

## 三、元数据与持久化（Section 2.6）

三类元数据**全部驻留内存**，但**只有两类写日志持久化**：

| 元数据 | 持久化？ |
|---|---|
| 文件与 chunk 的命名空间 | ✅ 操作日志 |
| 文件 → chunk 的映射 | ✅ 操作日志 |
| **chunk 的副本位置** | ❌ **不持久化** |

**位置为什么不持久化**：chunkserver 才是"某个 chunk 在不在我盘上"的**最终权威**。上千台机器的加入、离开、宕机、坏盘极其频繁，master 维护一份持久视图既昂贵又必然过时。做法是 master 启动时轮询一遍，之后靠 **HeartBeat** 持续同步。

> 可泛化的原则：**能从别处重建的状态就不要持久化**。它同时消除了 master 与 chunkserver 之间的一致性维护问题。

**操作日志**：
- 元数据**唯一的持久化记录**，同时充当定义并发操作先后的**逻辑时间线**
- 必须**同时刷到本地磁盘和多台远程机器**之后，变更才对客户端可见
- **批量打包多条记录一起刷写**摊薄开销
- 日志超阈值就做 **checkpoint**：紧凑的**类 B 树结构，可直接映射进内存**无需解析；恢复只需加载最新 checkpoint + 重放少量后续日志。checkpoint 在**独立线程**创建，**不阻塞正在进行的变更**

## 四、读写流程（Section 2.4、3.1–3.2）

### 4.1 读

```
1. client 用应用传入的 (文件名, byte offset)，借助定长 chunk 算出 chunk index（纯除法，零 RPC）
2. client → master: (文件名, chunk index)
3. master → client: chunk handle + 副本位置列表   ← client 缓存
4. client → 最近的一个副本: (chunk handle, byte range)
```
后续对同一 chunk 的读**完全不需要 master**，直到缓存过期。

### 4.2 租约与变更定序

**总原则：最小化 master 在所有操作中的参与。**

- master 把 chunk 的 **lease** 授予一个副本，它成为 **primary**
- **primary 为该 chunk 上所有变更选定一个串行顺序**，所有副本严格遵循
- 全局顺序 = **master 授予租约的顺序** + **primary 分配的序列号顺序**
- 租约初始 **60 秒**，只要 chunk 还在被修改就能无限延期；**延期请求搭载在 HeartBeat 上，零额外开销**
- master 可主动**撤销**租约（快照要用）；即使和 primary 失联，也只需**等旧租约过期**就能安全改授他人

> **租约的精髓**：用**时间**换取**互斥的安全性**。master 不需要联系上旧 primary，就能确信它已无权定序，因此不会脑裂 —— 也就不需要任何分布式共识。代价是最长 60 秒的写不可用窗口。

### 4.3 写入七步

```
1. client   → master        : 谁持有租约？副本都在哪？
2. master   → client        : primary 身份 + secondary 位置        (client 缓存)
3. client   → 所有副本       : 推送数据（顺序任意，先进 LRU 缓冲区，尚未写入文件）
4. client   → primary       : 发出写请求；primary 给并发变更分配连续序列号，先本地应用
5. primary  → 所有 secondary : 按相同序列号顺序应用
6. secondary→ primary       : 完成确认
7. primary  → client        : 返回结果（任一副本出错都会上报）
```

**关键：第 3 步的数据推送与第 4–7 步的控制流完全解耦。** 数据走网络拓扑最优路径，控制消息只是很小的包。

失败时该区域处于不一致状态；客户端先**重试 3–7 步**，仍不行才从头开始。**跨 chunk 边界的大写入会被客户端库拆成多个操作** —— 这是并发写产生 undefined 区域的具体来源。

### 4.4 数据流为什么是"链"不是"树"

| 目标 | 手段 |
|---|---|
| 用满每台机器的**出口带宽** | 沿**线性链条**依次传递（A→B→C），而非客户端向所有副本树形分发 |
| 避开瓶颈与高延迟链路 | 转发给拓扑上**最近的、尚未收到数据**的机器（Google 网络规整，可直接从 IP 估距离） |
| 最小化延迟 | **TCP 流水线**：收到一部分立刻转发，不等收完 |

理论耗时 `B/T + RL`（B=字节，T=吞吐，R=副本数，L=单跳延迟）→ 论文环境下 **1MB 约 80ms 分发到全部副本**。

> 若客户端一次发三份，它自己的出口带宽会被三等分而成为瓶颈。链式把多副本写的代价从**带宽 ×3** 降成了**延迟 +RL**，而 `RL` 相对传输时间很小。

## 五、Atomic Record Append（Section 3.3）

**解决什么问题**：传统写入要客户端指定 offset，几百个客户端并发写同一文件就必须上分布式锁。GFS **把 offset 的决定权收归系统**：客户端只给数据，GFS 决定位置并**返回实际 offset**。

**primary 的额外逻辑**：
- 若追加会让当前 chunk 超过 64MB → 把当前 chunk **padding 到 64MB**，通知 secondary 同样处理，让客户端**在下一个 chunk 上重试**
- 否则正常追加，要求所有 secondary 写在**完全相同的偏移量**

**限制**：单次 append 不超过 chunk 的 **1/4（16MB）**，把最坏情况的碎片控制在可接受水平。

**语义是 at-least-once**：任一副本失败就整体重试，各副本可能残留**不完整片段**或**重复记录**。因此 **GFS 明确不保证副本字节级相同**，只保证"数据被原子地至少写入一次到同一个 offset"。

> **这个折中为什么好**：应用天然把文件当**生产者-消费者队列**或做**多路归并**，本来就在用唯一 ID 去重、用校验和跳过坏记录。GFS 只提供应用真正需要的最弱保证，把复杂度留在应用层那点去重逻辑里，而不是在文件系统里实现一套分布式锁。

## 六、一致性模型（Section 2.7）

**两个概念**：
- **consistent**：所有客户端从**任何副本**读到的数据**都相同**
- **defined**：consistent，**并且**能看到某次变更**完整写入的内容**（没被并发变更切碎）

`defined ⟹ consistent`，反之不成立。

**Table 1（论文原表）**：

|  | Write | Record Append |
|---|---|---|
| **串行成功** | defined | **defined，其间夹杂 inconsistent** |
| **并发成功** | **consistent but undefined** | **defined，其间夹杂 inconsistent** |
| **失败** | inconsistent | inconsistent |

容易记错的两点：
- 并发 write 成功 → 副本**内容相同**（都按同一顺序应用），但是**多次写的片段混杂**，不对应任何单次写 → consistent 但 undefined。
- record append 即使**串行**也是 "defined interspersed with inconsistent" —— 重试会在副本间留下 padding 和重复片段；**夹缝区域** inconsistent，但每条**成功写入的记录本身**是 defined 的。

**GFS 靠什么撑住这个保证**：① 所有副本按相同顺序应用变更；② **chunk 版本号**检测过期副本；③ HeartBeat 检测失效 chunkserver，**校验和**检测静默损坏。只有一个 chunk 的**所有副本在 master 反应过来之前全部丢失**，数据才真正丢失 —— 即便如此系统也是**明确报错**，而非返回损坏数据。

**代价转嫁给应用（2.7.2）** —— 这是理解 GFS 一致性模型的另一半：
- **优先追加而非覆盖写**；写完临时文件再**原子重命名**；或定期 **checkpoint**，读者只读到最新 checkpoint 为止
- 记录**自带校验和**，读取时跳过 padding 和不完整记录
- 记录**自带唯一标识符**，读取时去重

## 七、Master 的后台工作（Section 4）

**命名空间与锁（4.1）**
- **没有 per-directory 结构**，**不支持软硬链接**。命名空间就是一张查找表：全路径名 → 元数据，内存中前缀压缩
- 每个节点一把**读写锁**；操作先取路径上所有父目录的**读锁**，再取目标的读锁或写锁
- **创建文件不需要父目录的写锁**（没有目录项列表要保护）→ **同一目录下可并发创建大量文件**
- **防死锁**：按树的**层级排序**，同层按**字典序**取锁

**副本放置（4.2）**：必须**跨机架**。整机架掉线（共享电源/交换机）仍有副本，且读能吃到**多机架聚合带宽**；代价是写流量必须跨机架 —— 刻意的权衡。

**创建 / 再复制 / 再平衡（4.3）**
- 创建时优先选**磁盘利用率低于平均**的机器；**限制单机"最近创建"的 chunk 数**（创建可靠地预示紧接着的大量写流量）；跨机架
- 再复制优先级：**离目标副本数差得越多越优先**；活跃文件优先；**正在阻塞客户端进度的最优先**
- 全程**限流**：限制并发克隆数与克隆读速率。新 chunkserver **逐步填充**，而非立刻被新 chunk 和写流量淹没

**垃圾回收（4.4）—— 惰性删除**
1. 删除**立即写日志**，文件改名为带时间戳的**隐藏名**
2. 宽限期内（默认 **3 天**）仍可读，改回原名即可**反删除**
3. 超期后 master 扫描命名空间移除隐藏文件，切断与 chunk 的关联
4. 另一轮扫描识别**孤儿 chunk**，清除元数据
5. 通过 **HeartBeat** 告知 chunkserver 哪些 chunk 已不存在，由它自行删除本地副本

> **为什么惰性更好**：在故障常态化的系统里，"创建可能部分成功""删除消息可能丢失"是常态。惰性 GC 提供**统一的兜底** —— 任何"不知来源"的无用副本都由同一套逻辑清掉，不需要为每种失败路径写补偿代码。开销还能**批量摊薄到空闲时段**，并顺带成为防误删的安全网。缺点是空间紧张时妨碍精细调优（可重复删除以加速回收，或对不同命名空间配不同策略）。

**过期副本检测（4.5）—— chunk version number**
- master **每次授予新租约时递增版本号**，通知所有最新副本，双方**都持久化记录**；这发生在**任何客户端被告知该 chunk 信息之前**
- 宕机的 chunkserver 错过递增 → 重启上报时 master 发现**版本号偏低** → 判定过期，当它不存在，等 GC 清掉
- 若某副本版本号**高于** master 的记录，master 认为是自己授租约时挂了，**采纳更高的版本号**

**快照（3.4）—— copy-on-write**
1. **先撤销租约** —— 逼后续写入重新问 master，给 master 拦截的机会
2. **写日志 + 复制元数据** —— 快照文件指向**完全相同的 chunk**，一个字节都不复制，只是引用计数 +1
3. **写时才真正复制** —— master 发现引用计数 > 1，**推迟回复客户端**，先让持有原副本的 chunkserver **在本地磁盘上**复制出 C'，再对 C' 授租约

> 要求**同机复制**，走本地磁盘 I/O 而非网络（当时本地磁盘约为 100 Mbps 网络的三倍快）。分裂成 C（快照持有，冻结）和 C'（源文件持有，可改）才能保证快照的隔离语义。

## 八、容错与数据完整性（Section 5）

**快速恢复**：master 和 chunkserver 都能在**数秒内**重启恢复。GFS **不区分正常与异常终止**，服务器就是直接 kill 掉的 —— 这强迫恢复路径成为**常用代码路径**，因此总是被测试过的。

**master 复制**：
- 操作日志和 checkpoint 复制到多台机器，**写入所有副本磁盘后变更才算提交**
- master 进程挂了立即重启；机器彻底损坏则由**外部监控**在别处用复制的日志**启动新 master**
- 客户端通过 **DNS 别名**访问，迁移时改别名即可
- **shadow master** 提供**只读访问**，滞后**通常不到一秒**。因为文件内容来自 chunkserver，应用**不会读到过期的文件内容**，可能过期的只是**元数据**

> ⚠️ GFS 任何时刻只有**一个** master 处理变更。master 副本用于**灾后重建**（平时不服务请求），shadow master 用于**读可用性**。**不是多主对等架构，也没有自动 failover 选主** —— 切换依赖外部监控系统。这正是后续 Raft/Paxos 要解决的问题。

**数据完整性：校验和（5.2）**

**为什么不靠比对副本**：GFS 的变更语义（尤其 record append）**不保证副本字节相同**，副本分歧可能是**合法的**。所以**每台 chunkserver 必须独立验证自己的副本**。

- **组织**：chunk 分成 **64KB 的块**，每块一个 **32 位校验和**，存内存 + 写日志持久化，与用户数据分开存放
- **读路径**：返回数据前先校验涉及的块 → **损坏绝不会传播到其他机器**。不匹配则向请求方报错 + 向 master 报告 → 请求方转向其他副本，master 从别处克隆，随后指示删除损坏副本
- **写路径**（体现"为追加优化一切"）：**追加**只需**增量更新**最后一个部分填充块的校验和 —— 即使那个末尾块已损坏而未被察觉，新校验和也不会匹配，下次读取照常暴露；**覆盖写**则必须**先读取并验证首尾两个块**，否则新校验和会**掩盖未覆盖区域中已有的损坏**
- **空闲期扫描**不活跃的 chunk，防止**损坏但闲置的副本欺骗 master**，让它误以为有足够有效副本

> 校验和机制的直接动因是踩过的坑：某些磁盘声称支持某范围的 IDE 协议版本，实际只对新版本可靠响应，导致内核误判磁盘状态，**数据被悄无声息地损坏**。

## 九、设计哲学

1. **把故障当常态设计** —— 复制、监控、自动恢复是主干逻辑而非错误处理分支；直接 kill 服务器，逼恢复路径变成被反复执行的常用路径。
2. **控制流与数据流分离** —— 元数据集中、数据平面去中心化，这是"单点组件 + 海量吞吐"能共存的根本原因，后来的 HDFS、Ceph、对象存储都是这个套路。
3. **只持久化重建不出来的信息** —— chunk 位置由 chunkserver 上报，一举消除 master 与 chunkserver 的一致性维护问题。
4. **用租约把定序权下放** —— master 只决定"谁是 primary"，并用**超时**代替分布式共识来保证互斥安全。
5. **按负载精确放弃通用性** —— 放弃 POSIX、强一致、小文件优化、低延迟，每一次放弃都换来系统某处的大幅简化，而不是能力不足。
6. **惰性贯穿始终** —— 惰性空间分配、惰性 GC、惰性锁分配、copy-on-write，统一思路是**把开销推迟到能批量摊薄、且系统空闲的时刻**。
7. **让应用分担它本来就能分担的复杂度** —— 应用本来就要给记录加校验和与唯一 ID，文件系统就没必要为严格语义把自己搞复杂。这是"协同设计"的实质。

## 十、局限

| 局限 | 表现 |
|---|---|
| **单 master 是可用性单点** | 无自动 failover 选主，依赖外部监控重启或在别处拉起，切换期间写不可用 |
| **master 内存是容量上限** | 元数据全内存，文件数增长到一定规模后单机装不下 |
| **一致性弱，复杂度外溢** | 重复记录、padding、undefined 区域都要应用自己处理 |
| **不适合小文件** | 元数据开销与热点问题都在小文件上放大 |
| **不适合低延迟** | 所有设计都在拿延迟换吞吐 |
| **随机覆盖写效率差** | 支持但未优化，并发覆盖写只能拿到 undefined |

**为什么当时不用 Paxos 做多 master**：单 master 让复杂的放置、再复制、再平衡策略可以基于**全局信息**做出，实现难度低一个数量级；可用性靠日志复制 + 外部监控快速重启兜底，配合 shadow master 保住读。对批处理负载够用。

**与 HDFS 的关系**：HDFS 基本是 GFS 的开源复刻（NameNode ↔ master，DataNode ↔ chunkserver，block ↔ chunk）。主要差异是 HDFS **只支持单写者追加、不支持 record append**，一致性模型因而更简单。

**后续演进**：Google 内部演进为 **Colossus**，把元数据层本身分布式化以突破单 master 的内存与可用性上限，并用纠删码替代部分三副本。*（论文之外的背景。）*
