# MapReduce 论文读书笔记

> Dean & Ghemawat, *MapReduce: Simplified Data Processing on Large Clusters*, OSDI 2004

---

## 零, 一句话核心

**用受限的编程模型, 换取自动并行化和透明容错.**

用户只写 Map 和 Reduce 两个纯函数, 放弃任意控制流的自由; 作为交换, 框架自动完成分片; 调度; 容错; 负载均衡; 局部性优化. 

这是论文自己在结论里写的第一条教训, 也是后续 Spark / Flink / serverless 计算框架共同的思路源头. 

---

## 一, 三方通信

### 总原则

**master 只传控制信息和元数据, 真正的数据只在 worker 之间直接流动.**

📎 **完整时序图见 [`mapreduce-communication.html`](./mapreduce-communication.html)**（浏览器直接打开）

把控制流和数据流拆开数, 一共八条（论文本身没有这样枚举, 这是为了看清哪一条承载数据）: 

| 通路 | 内容 | 关键机制 |
|---|---|---|
| master → map | 分配任务: input split 文件名 + 字节范围 | 优先选持有该副本的机器 = locality 优化 |
| map → master | 完成汇报: R 个中间文件的位置和大小 | **重复汇报被忽略**, 重执行去重靠这条 |
| master → reduce | 分区号 + 中间文件位置 | **位置增量推送** → shuffle 能与 map 阶段重叠 |
| reduce → map | RPC 请求: "给我第 k 号分区那一段" | 位置来自 master, 不是问 map 要的 |
| **map → reduce** | **本分区的实际数据** | **唯一的数据通路, 1TB 全在这条线上** |
| reduce → master | 完成汇报 | 临时文件已原子 rename 成最终输出 |
| master ↔ worker | 心跳 ping / pong | 响应搭车带回计数器值; 超时 → 该机已完成的 map 任务重跑 |
| worker → master | 坏记录序号（UDP last gasp） | 进程正在死, 来不及 TCP 握手 |

**量级对照**: 所有控制消息加起来, 整个 job 经过 master 的元数据约 60MB; 那一条数据通路独自承载 1TB. **差四个数量级** -- 这就是单 master 能服务 1700 台 worker 的原因. 

### 位置与数据: 链路上的三步

```
1. map 完成      → 汇报给 master: R 个文件在本地盘的什么位置
2. master 转发    → reduce worker 知道了"去哪儿拿", 但还没有一个字节的数据
3. reduce 发 RPC  → 这一步才真正把数据搬过来
```

**位置信息来自 master, RPC 拉的是数据本身** -- 不知道位置根本发不出这个 RPC. 严格说所有通信都是 RPC, 但只有第 3 步承载大流量. 

三个推论: 

- **位置为什么必须集中在 master**: map 任务完成后进程就退出了, 没人可问; reduce worker 也不知道该问 1700 台里的哪几台. 
- **位置是增量推送的**: master 每收到一批新汇报就推给 reduce worker. 这是 shuffle 能和 map 阶段重叠的机制基础（5.3 节: 第一批 map 完成后 shuffle 就开始了）. 
- **map 和 reduce 之间没有控制层通信**: map 不知道谁会来读, reduce 也不预告, 全靠 master 转述位置建立关联. 这个松耦合让 map 进程可以完成即退出, 不必活到所有 reducer 取完. 

master 因此只存两类状态（3.2 节）: 每个任务的状态（idle / in-progress / completed）+ 所在 worker; 每个**已完成 map 任务**的 R 个中间文件位置和大小 -- 后者就是 **O(M×R)** 的来源, 15000 × 4000 ≈ 6000 万条约 60MB. **"元数据集中; 数据分散"** 与 GFS 的 master/chunkserver 完全一致, 同一个团队; 同一套设计哲学.

## 二, 必须记住的机制

### 1. 中间数据写本地盘, 不写 GFS

**动机**: 省掉 3 倍写放大和跨网络流量. 网络带宽是全系统最稀缺的资源. 

**代价**: 中间数据没有冗余副本. 

注意: worker 机器故障时, **它上面已经完成的 map 任务也要重跑** -- 数据躺在那台机器的本地盘上, 机器挂了就没了, 而全部 R 个 reducer 都指望着从它那儿取自己那一份. 

对比: 已完成的 reduce 任务**不需要**重跑, 输出在 GFS 上. 

### 2. 原子提交保证 exactly-once 语义

只要用户的 Map/Reduce 是确定性函数, 分布式执行结果与顺序执行完全一致. 

- **map 完成**: 把 R 个临时文件 rename 到位, 汇报给 master; **master 忽略已完成任务的重复汇报**
- **reduce 完成**: 把临时文件原子 rename 成最终文件名

依赖底层文件系统 rename 的原子性. 有了这套机制, backup task 和故障重执行才是安全的 -- **去重逻辑本来就是为故障重执行设计的, backup task 只是复用它, 没有引入任何新的一致性机制**. 

这条"分布式执行 == 顺序执行"的语义保证, 也正是本地顺序执行能用来调试的前提（3.3 节）. 

### 3. Backup task 对付 straggler

job 接近尾声时, 对**仍在运行的任务**统一发起冗余执行, 谁先完成算谁的. 

**备份任务不接管任何进度, 从零重算:**
- 备份 **map** 任务: 自己去 GFS 读输入（仍走 locality 优化）. 如果原机器是坏盘导致慢, 备份读的是另一个副本; 另一块盘, 完全绕开病灶. 
- 备份 **reduce** 任务: 整个 shuffle 重做一遍, 代价大得多. 

**这就是为什么只在接近完成时才启动** -- 全程双发会把网络和磁盘打爆. 

> 关掉 backup task, 1TB 排序从 891 秒变成 1283 秒, **慢 44%**. 最后 5 个 straggler 拖了近 1000 秒. 

### 4. Locality 优化

GFS 每块存 3 副本, master 尽量把 map 任务调度到**持有该输入副本的机器**上, 或同机架的机器. 大部分输入读取不消耗网络带宽. 

这解释了 5.3 节一个反直觉现象: 输入速率 > shuffle 速率 > 输出速率. 输入走本地盘, shuffle 走网络, 输出走网络且写两份副本. 

### 5. 任务数远大于机器数

M = 15000, R = 4000, 机器 1746 台. 一台机器**先后**执行多个任务. 

| | 含义 | 谁决定 |
|---|---|---|
| **M** | input split 数 = map 任务数 | 由分片大小算出（16–64MB, 对齐 GFS 块）|
| **R** | 分区数 = reduce 任务数 = 输出文件数 | 用户直接指定 |

**为什么要远大于机器数**: 
- 动态负载均衡: 快机器自然多领任务
- 故障恢复快: 重跑的是 8~9 个小任务, 还能分散并行
- locality 更好调度: 粒度细, 更容易找到持有副本的空闲机器

**上限**: 
- master 的 O(M×R) 状态
- 中间文件碎片化（见下）

### 6. Shuffle 的实际形态（M × R 全连接）

```
15000 个 map 任务 × 4000 个 reduce 任务 = 6000 万次读取
每个 map 输出 1TB/15000 ≈ 64MB, 切成 4000 份 → 每份约 16KB
```

每个 reducer 要触及**全部** 15000 个 map 任务的输出, 因为它负责的 key 区间散落在每一个 map 任务里. 

**16KB 是个痛点**: 机械盘一次寻道约 10ms, 读 16KB 只要零点几毫秒, 几乎全是寻道开销. 

缓解手段: 
- **按机器合并**: 15000 个任务只在 1746 台机器上, 一次连接取 8~9 段 ≈ 140KB, 连接数从 6000 万降到约 700 万
- **page cache**: 中间文件刚写不久, 很可能还在内存里
- **错开访问顺序**: 避免所有 reducer 都从同一台机器开始拉

**这是 M; R 不能无脑调大的真实原因** -- 粒度够细 vs 读取够连续, 是一对矛盾. 

### 7. 每个 reducer 的工作量（尺度感）

排序作业: 1TB / 4000 ≈ **250MB**, 250 万条记录. 

250MB 能塞进内存（4GB 机器扣掉别的任务还剩 2.5GB+）, 所以排序在内存里完成, 不需要外部归并.**选 R = 4000 的一个隐含目标就是让分区落在内存能吃下的范围.**

R 太小很危险: R=100 时每个 reducer 要处理 10GB, 必然触发外部排序, 同时任务粒度变粗; 负载均衡和故障恢复都变差. 

**决定 R 的是中间数据量, 不是输入量.** grep 的 R=1 完全没问题, 因为输出只有 9 万条命中.

## 三, 其他值得记住的内容

### Combiner 的前提条件（论文没大字强调, 但很关键）

**Reduce 操作必须满足交换律和结合律.**

- 求和; 求最大值: 可以
- 求平均值: **不行**, `avg(avg(1,2), avg(3)) ≠ avg(1,2,3)`. 要改成输出 `(sum, count)` 对才能合并

Combiner 和 Reduce 代码通常一模一样, 唯一区别是**输出去向**: Combiner 写中间文件（要发给 reduce）, Reduce 写最终输出文件. 

### 全局排序 = 两个原语的组合

**MapReduce 本身没有实现任何"分布式排序算法"**, 它只提供两个原语, 用户一组合就得到全局排序, 代码不到 50 行. 

```
全局有序 = 分区之间有序 + 分区内部有序
           ↑                ↑
      范围分区函数（4.1）   reduce 天然排序（4.2, 免费）
```

**核心认知: 分区之间的有序不是"排"出来的, 是"分"出来的.**

分区函数改成范围划分而非 hash: 

```
分区 0 只接收  key < "d"
分区 1 只接收  "d" ≤ key < "s"
分区 2 只接收  key ≥ "s"
```

一旦规则如此, "分区 0 的任何 key < 分区 1 的任何 key"就是规则的**直接推论**, 不需要任何机器去验证. 像按邮编分拣信件, 箱子之间的顺序在分拣那一刻就定了. 

**三个易错点**: 
1. 所有 mapper 必须用**同一份**边界数组, 否则分区语义崩溃 → 所以采样必须是独立的前置作业
2. 换成 hash 完全不成立: 分区内仍有序, 但拼起来是垃圾
3. 边界靠**采样取分位点**确定, 避免数据倾斜（TeraSort 的 key 是随机字节, 分布均匀, 所以论文直接跳过了采样）

### 跳过坏记录的巧妙之处

1. signal handler 捕获 SIGSEGV / SIGBUS
2. 调用用户函数**前**把记录序号存入全局变量
3. 崩溃时发 UDP 包给 master（**用 UDP 是因为进程正在死, 来不及 TCP 握手**）
4. master 见同一记录**失败两次**才指示跳过（**防止把一次性的机器故障误判成确定性坏记录**）

### 计数器的正确性细节

worker 的计数值**搭 ping 响应的便车**发给 master（复用已有心跳通道, 零额外开销）. 

**master 只累加成功完成的任务的计数, 且每个任务只算一次** -- 否则 backup task 和故障重执行会造成重复计数. 

### 关键数字

| 项目 | 数值 |
|---|---|
| 关掉 backup task | 排序慢 **44%**（891 → 1283 秒）|
| 杀掉 200 个 worker | 只慢 **5%**（891 → 933 秒）|
| 索引系统重写 | 3800 行 → **700 行** C++ |
| 平均每 job 故障机器数 | **1.2 台**（157 台机器规模）|
| 1TB 排序 / grep 1TB | 891 秒 / 150 秒（含 60 秒启动开销）|
| 累计（至 2004.08） | 29423 个 job, 输入 3288TB → 中间 758TB → 输出 193TB |

**三个耗时数字放一起看, 就是全文的论证**: 

> 故意制造的大规模故障（+5%）, 代价远小于放任几个慢节点（+44%）. 

**"平均每 job 故障 1.2 台机器"** 是全文的立论基础 -- 在这个规模下故障是常态不是异常, 容错不是可选项. 

**输入 3288TB → 输出 193TB** 的漏斗形状说明典型作业是"大量输入; 大幅归约", 和排序那种 1:1:1 的极端情况相反. 

### 6.1 索引系统: 被低估的真正价值

3800 → 700 行只是表象. 真正的改变是**扫描变便宜之后, 人们才敢按逻辑清晰度; 而不是性能压力来组织代码** -- 不必再把不相关的逻辑硬塞进同一遍扫描来摊薄成本. 原来几个月的改动变成几天. 

### 这篇论文的边界

- **不适合低延迟和小作业**: grep 的 150 秒里 60 秒是启动开销（分发二进制; 打开 1000 个 GFS 文件; 获取 locality 信息）
- **不适合迭代计算**: 每轮中间结果都要落盘再读回, 机器学习那类反复迭代代价极高 → 这正是 Spark 用内存 RDD 切入的空档
- **单 master 无高可用**: 论文坦承实现里 master 挂了整个 job 重来, 靠概率低搪塞
- **原创性有限**: Related Work 自己承认 map/reduce 原语来自函数式语言; 分布式排序数据库早有; 冗余执行 River 做过. 贡献在于**特定约束下的组合**

### 两种 straggler 哲学（7 节）

River 精确预测并动态调平生产者/消费者速度; MapReduce 不预测, 用细粒度任务 + 冗余执行兜底. 后者简单粗暴, 但在几千台机器; 故障率高的环境里更鲁棒 -- 这个取舍在后来的分布式系统里反复出现. 

### 非确定性函数的弱保证

如果用户的 Map 是非确定性的, backup task 的 A 和 B 可能产出不同中间结果, 不同 reduce 任务可能读到来自不同执行的数据. 语义退化成"每个 reduce 任务的输出对应某一次顺序执行, 但整体不一定对应同一次"（3.3 节末尾）.

## 四; 写 Lab 1 时的自检

**每写一段代码, 试着说出它对应哪个约束.**

| 设计决策 | 对应的约束 |
|---|---|
| 中间数据不写 GFS | 网络带宽稀缺 |
| 已完成的 map 任务在机器故障时要重跑 | 上一条的直接代价 |
| 任务数远大于机器数 | 故障是常态 + 机器速度不均 |
| 重执行而非复制来容错 | 廉价机器, 计算比存储便宜 |
| 分片对齐 16–64MB | GFS 块大小 + 寻道开销 vs 粒度的平衡 |
| 原子 rename 提交 | 必须支持重复执行 |
| master 只存元数据 | 单 master 不能成为带宽瓶颈 |
| backup task 只在尾声启动 | 冗余执行代价高, 只值得为尾部延迟付 |
